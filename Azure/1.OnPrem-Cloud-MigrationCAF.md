## 3-tier application Single-Region with Disaster Recovery (DR) baseline
#### Architecture Context  
  - `Presentation Tier`: Web Frontends / APIs  
  - `Application Tier`: Business Logic / Microservices  
  - `Data Tier`: Relational Database (SQL) & State / Cache (e.g., Redis)  

#### Step 1: Strategy & Discovery (CAF Alignment)
  ##### Establishing RTO, RPO, and Financial Baseline
  For a 3-tier application, different components carry different tolerances for downtime and data loss.
  - `RTO` (Recovery Time Objective):  
    - `Web/App Tier`: Near zero (stateless, easily redeployed via CI/CD or auto-scaled).
    - `Data Tier`: (State) Defines how fast database failover to the DR region must complete (e.g., $< 15$–$30$ minutes).
  - `RPO` (Recovery Point Objective):
    - `Transactional Data`: Target $< 5$ minutes (requires real-time or near-real-time asynchronous transaction log streaming).
  - `Financial Assessment (TCO / ROI):`
    - Evaluate current compute, storage, networking, licensing, and operational costs on-premises.
    - Estimate cloud run costs (Primary region + secondary DR standby costs) using the Azure TCO Calculator.
  ##### Application Rationalization (The "5 Rs" Decision)
  Each tier of a 3-tier stack may require a distinct migration pattern:
  Tier,Component Example,Chosen Strategy,Rationale
| Tier              | Component Example           | Chosen Strategy                | Rationale                                                                                                                                                 |
|--------------------|-----------------------------|--------------------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------|
| Presentation Tier  | Web Servers / Gateways      | Rehost (Lift & Shift) or Refactor | Move IIS/Nginx VMs to Azure VMs or containerize into Azure App Service / AKS.                                                                            |
| Application Tier   | Business Logic / APIs       | Refactor / Repackage            | Move stateful apps to stateless microservices to simplify active-passive and active-active failover.                                                     |
| Data Tier          | Relational DB / Cache       | Replatform                      | Move self-hosted DBs (e.g., SQL Server, Postgres) to Azure SQL Managed Instance or Flexible Server to offload replication and failover overhead.          |

###### migration strategy
"5 Rs" of application rationalization
 - **Rehost ("Lift and Shift")**: moving on-premises infrastructure to cloud infrastructure (IaaS VMs) without making any changes
 - **Refactor ("Repackage")**: Making minor code modifications, configuration tweaks, or containerizing the application so it can leverage Managed Platform-as-a-Service (PaaS)
       - Presentation/App Tier: Packaging IIS/Nginx web apps into Docker containers to run on Azure App Service or Azure Kubernetes Service (AKS).
       - Data Tier: Replatforming self-hosted databases to Azure SQL Managed Instance or PostgreSQL Flexible Server to eliminate DB administrative overhead.

- **Rearchitect**: Significantly modifying and extending the application code and architecture to make it `cloud-native`.
      - App Tier: Breaking down a monolithic business logic tier into event-driven microservices (e.g., using Azure Functions, Event Grid, or AKS).
      - Data Tier: Splitting a monolithic relational database into domain-specific databases or moving to distributed/NoSQL models (e.g., Azure Cosmos DB or CockroachDB) for active-active multi-region reads and writes
  **Rebuild ("Cloud-Native Rewritten")**
      - rewriting business logic using modern frameworks (e.g., Node.js, Go, Python), leveraging native cloud services like Azure Logic Apps, API Management, Serverless Functions

  #### Step 2: Ready Phase (Azure Landing Zones)
  - 1. Establish Hub-and-Spoke virtual networks across Primary Region (East US) and Secondary DR Region (West US).
  - 2. Configure Global VNet Peering to allow private cross-region replication traffic over the Azure backbone.
  - 3. Deploy centralized identity (Entra ID), Key Vaults, and Azure Policy constraints.

  #### Step 3: Landing Data Tier
  - 1. Primary Database Setup: Deploy Azure SQL DB / PostgreSQL Flexible Server in Primary Region.
  - 2. Replication Setup: Enable Active Geo-Replication (or Auto-Failover Groups) to stream database binary logs asynchronously to the secondary region replica.
  - 3. Cache Setup: Deploy Redis Cache in primary region; provision cold/warm standby Redis instance or geo-replication in secondary region.
   
#### Step 4: Compute & Network Deployment
- 1. Deploy Kubernetes Clusters (AKS) or App Services in both Primary and Secondary regions.
- 2. Set up Azure Front Door or Traffic Manager with health probes checking the primary region ingress.
- 3. CI/CD Pipeline Configuration: Configure pipelines to build once and deploy application artifacts to both regions simultaneously.

#### Step 5: Data Migration & Cutover
- 1. Perform initial bulk data copy from On-Premises to Primary Cloud DB.
- 2. Enable Continuous Change Data Capture (CDC) or log shipping to keep On-Premises and Primary Cloud DB in sync.
- 3. Cutover Execution:
     - Put application into read-only mode on-premises.
     - Allow remaining sync changes to drain to Cloud Primary DB.
     - Update DNS / Azure Front Door routing to point to Cloud Primary.
     - Validate post-migration health and open site to public.

### PHASE 2: Transitioning to Active-Active Multi-Region
To move from a passive standby DR setup to a fully Active-Active Multi-Region architecture, you eliminate the single-primary bottleneck by shifting data and routing logic to handle writes across multiple regions simultaneously.
```
+----------------------------------------------------+
               |           Azure Front Door / Traffic Manager       |
               |       (Global Anycast / Geo-Proximity Routing)     |
               +-----------------+----------------------------------+
                                 |
              +------------------+------------------+
              | (Active Region 1)                   | (Active Region 2)
              v                                     v
+---------------------------+         +---------------------------+
| Ingress / Web Frontend    |         | Ingress / Web Frontend    |
+-------------+-------------+         +-------------+-------------+
              |                                     |
              v                                     v
+---------------------------+         +---------------------------+
| Application Services      |         | Application Services      |
+-------------+-------------+         +-------------+-------------+
              |                                     |
              +------------------+------------------+
                                 |
                                 v
+-----------------------------------------------------------------+
| Multi-Region Active-Active Database Layer                       |
| (Azure Cosmos DB Multi-Master OR CockroachDB Distributed SQL)   |
| - Automatic Consensus / Conflict Resolution                     |
| - Bi-Directional Async/Quorum Replication                       |
+-----------------------------------------------------------------+
```
#### Step 1: Rethinking the Data Tier Strategy
Relational databases with single primaries cannot natively accept concurrent writes in two regions without significant locking latency or split-brain risks.
- Option A: NoSQL Multi-Master (Azure Cosmos DB)
  - Enable Multi-Region Writes.
  - Use Last-Write-Wins (LWW) or custom conflict resolution stored procedures for concurrent updates.

- Option B: Distributed Cloud-Native SQL (CockroachDB / YugabyteDB)
  - Uses Raft Consensus micro-sharding across 64MB Ranges.
  - Writes require majority quorum across regions.
  - Use REGIONAL BY ROW schema patterns so US user rows are written locally in US nodes and EU user rows in EU nodes.

#### Step 2: Application Layer Decoupling & Statelessness
- `Stateless Session Management`: Store user sessions in external distributed caches (e.g., Redis Enterprise active-active geo-distribution) or move to stateless JWTs so any region can handle any request.
- `Asynchronous Messaging`: Replace synchronous cross-region HTTP dependencies with event-driven architectures using Azure Event Hubs or Kafka with geo-replication.

#### Step 3: Traffic Management & Edge Routing
 - 1. Configure Azure Front Door with latency-based dynamic routing (Anycast BGP).
 - 2. Incoming user traffic automatically lands on the geographically closest healthy region.
 - 3. If Region 1 fails, Azure Front Door instantly redirects active user traffic to Region 2 within seconds without requiring manual failover procedures.

#### Step 4: Phased Multi-Region Deployment Sequence
 - 1. Dark Launch (Region 2):eploy compute services to Region 2; run internal load testing while production traffic remains on Region 1.
 - 2. Data Dual-Writing / Synchronization Verification: Ensure global database consistency models operate within expected latency bounds under synthetic write stress.
 - 3. Weighted Traffic Split (Canary Rollout):
      - Route 10% of live global user traffic to Region 2 via Front Door.
      - Monitor database latency, transaction rollbacks, and conflict resolution metrics.
      - Incrementally ramp up traffic: 25% $\rightarrow$ 50% $\rightarrow$ 100% (Active-Active).
